fix: attribute a reused benefit ID to the campaign that awarded it

This is the actual cause of the ALGS Split 2 PL charm being lost, and it is not
what fad4809, b94789b or a130401 addressed. Those protected fields Twitch
omitted. Here nothing was omitted: the reward was marked claimed when it never
had been.

mergeInventory derived claim state solely from benefit-ID presence, deliberately
— "SOURCE OF TRUTH: Only check inventory benefit IDs." That holds only while a
benefit ID identifies one campaign, and Twitch reuses them freely. The charm
carries the same benefit on MD4, MD5 and MD6; only the drop id changes, which is
why its progress restarted from zero each day. Claim it once, anywhere in the
event, and every later match day read it as already claimed. Each campaign was
then left with the 15-minute pack as its only earnable reward, so claiming that
pack emptied earnableDrops and the campaign was filtered as no_earnable_drops on
the very next refresh — matching the measured timing exactly, every miner
stopping ~2 minutes after its own claim, on all three days.

John's Drops screenshots are the proof: SwiftMiner shows the 60-minute charm
green-ticked as claimed in MD4 and MD5, while Twitch's own inventory shows it
greyed out, never obtained.

Not an ALGS quirk. 73 benefit IDs in one account's campaign set are shared
across campaigns, and 19 of 96 currently-active campaigns contain one. The worst
case is a single benefit spanning every tier of every daily affiliate campaign
for weeks: claim one tier once and all of them become permanently unearnable.

Benefit IDs stay the source of truth for whether a reward was claimed. What they
cannot say is where, so a shared benefit is now attributed by award time, which
does identify the campaign whose window contains it. An award Twitch dated
poorly, or one predating the campaign, leaves the reward earnable: a redundant
claim attempt is refused harmlessly, while a wrong "claimed" forfeits the reward
for good.

InventorySnapshot carries benefitAwardedAt for this; the timestamps were already
parsed into ClaimedBenefit.lastAwardedAt and simply never reached the merge.

Release notes now lead with this rather than with the omitted-field fix, which
was describing the symptom.
