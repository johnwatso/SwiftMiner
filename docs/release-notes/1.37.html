Stop /validate retiring a Twitch login that still works

An account imported from web cookies has no refresh grant and only a
fabricated expiry, so every launch took the revalidate path. That path
asked Twitch's /oauth2/validate, which speaks for Helix OAuth tokens and
rejects a cookie-derived one — while GraphQL, the API mining actually
runs on, kept accepting it. The 401 was read as proof the login had died,
which sent a re-authenticate DM on every single launch, and because the
throw skipped the re-arm the stale expiry survived to do it again.

Diagnostics from a 5-account instance show the miner connecting PubSub,
pulling 109 campaigns and selecting channels seconds after the "token has
expired" warning, finishing the session at needsAuth=false.

/validate can no longer retire a token: a rejection keeps it, logs why,
and re-arms a short window so relaunching stops re-probing. The window is
deliberately shorter than the confirmed-healthy one, because nothing has
verified this token's health. A real GraphQL rejection still force-
refreshes and surfaces authenticationFailed, so a genuinely dead login is
still reported.

performRefresh mapped every non-200 to tokenExpired, so a 429 or a Twitch
5xx would ask the user to sign in again over a transient blip. Only 400
and 401 — an outright refusal of the grant — do that now. That decision
is a pure refreshOutcome(forStatusCode:) so it can be tested, which it
now is across 200/400/401/403/429/500/502/503/504.

Ships in 1.37 build 2026080613.
